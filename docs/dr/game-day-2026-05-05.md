## 3. Esecuzione tabletop

### 3.1 Scenario A — Replay massivo DLQ (`runbook 01`)
- **Trigger simulato**: outage downstream Voispeed → 5k webhook in DLQ.
- **Walkthrough**: tracciato passo-passo del runbook contro lo schema reale di `incoming_requests`.
- **Esito**: ✅ runbook applicabile. Lo script `drill-dlq-replay.sh` referenzia colonne (`received_at`, `error_class`, `error_message`, `attempt_count`) **non presenti** nello schema corrente (`incoming_requests` ha `created_at`, `error_message`, `dlq_reason`, `status`). → **gap**.
- **RTO simulato**: < 4h confermato (replay batch da 500 ogni 60s).

### 3.2 Scenario B — PITR Restore (`runbook 02`)
- **Trigger simulato**: cancellazione massiva accidentale su `deals`.
- **Walkthrough**: identificazione T-recovery, restore in shadow project, validazione checksum, cutover.
- **Esito**: ✅ runbook applicabile. PITR infra è up (`wal_level=logical`, `archive_mode=on`). Drill `drill-pitr-validation.sh` legge correttamente `audit_events.occurred_at`.
- **RPO simulato**: < 5 min (PITR continuo). **RTO simulato**: ~90 min (entro target 2h).

### 3.3 Scenario C — Edge Functions Failover (`runbook 03`)
- **Trigger simulato**: edge runtime down regionale → tutte le `functions/v1/*` in 5xx.
- **Walkthrough**: attivazione `webhook_queue_only_mode` + banner sistema, stop dispatcher, drenaggio coda al ripristino.
- **Esito**: ✅ **CHIUSO 2026-05-05**: tabella `public.system_settings` creata con RLS (read=authenticated, write=admin), seed dei flag `webhook_queue_only_mode` e `system_banner` disabilitati, REPLICA IDENTITY FULL + pubblicata su `supabase_realtime`. Script `drill-edge-failover.sh` corretto (colonne reali `raw_body` invece di `payload`, `created_at` invece di `received_at`). Runbook 03 aggiornato (`dlq_reason` invece di `error_class`).
- **RTO target**: <30 min — non valutabile finché il toggle non è normalizzato.

## 5. Cosa ha funzionato

- WAL/PITR + audit pipeline solide: tutte le pre-condizioni infra DR verdi.
- Runbook 02 (PITR) eseguibile end-to-end senza modifiche.
- DLQ e outbound webhook con backlog trascurabile → la baseline operativa è sana, il DR partirebbe da uno stato pulito.
- SLO pipeline alimentata regolarmente (864 measurements/24h) → segnale affidabile per detection.

## 6. Cosa NON ha funzionato

- 2 dei 3 script di drill referenziano oggetti DB obsoleti: gli script erano stati scritti contro uno schema precedente e mai ri-validati. **Vero rischio**: in un incident reale, il primo `psql` fallirebbe e l'IC perderebbe minuti preziosi.
- Mancanza di un check di sanità schema in testa a ogni script DR.
- Cadenza dei backup non monitorata: l'ultimo backup è di 5 giorni fa e nessun alert l'ha segnalato.

## 7. Decisioni

1. **G2 è blocker** per dichiarare il runbook 03 "drill-ready": va chiuso entro 7gg.
2. **G1, G3 entro 14gg** (P1).
3. Prossimo game-day: **2026-11-05** (cadenza semestrale come da `README.md`).
